## 本轮新发现与修复复验结论

本轮（昨日会话）发现两个 bug，均已在提交 `2e0f7aa` 修复，今日完成复验：

1. **客户端断开 → 服务端 uncaughtException（已修复，复验通过）**
   - 原现象：SSE 客户端中途断开后，心跳/进度回调向已关闭的 controller 写入，抛 `TypeError: Invalid state: Controller is already closed`（uncaughtException），且管线在客户端离开后仍继续运行（后台 Whisper 子进程存活）。
   - 修复：`send()` 加 try/catch 守卫 + `request.signal` abort 监听中清心跳并关流 + finally 中关流加守卫。
   - 复验：干净内存下发起管线，2 秒后强制断开 → 后台管线正常跑完（47.4s，总结 ¥0.0033 + 视觉 ¥0.0017 正常记账），服务端日志零 uncaughtException/ERR_INVALID_STATE，服务存活。**通过**。

2. **DELETE /api/process 后缓存未失效（已修复，复验通过）**
   - 原现象：DELETE 删除帧文件后内存缓存未同步失效，同链接再处理返回 cached:true + 悬空帧引用（图片访问 404）。
   - 修复：DELETE 调用 `invalidateCache`（并顺带 `removeTranscript` + `clearConversation` 清理追问残留数据）。
   - 复验：(a) 处理后 cached:true + 6 帧可访问 → (b) DELETE 200、帧文件清空、同 videoId 追问 404（数据同步失效）→ (c) 同链接再处理 cached:false、完整管线重跑、重新抽帧 6 张。**通过**。

**残留观察（非用例失败，建议后续处理）**：
- 客户端断开后管线仍会继续后台运行至完成（消耗 LLM 成本）——修复 1 仅防崩溃，未做管线级取消。建议后续用 AbortSignal 传播取消下载/转写/总结。
- `%TEMP%\vidsnap` 下 `ffmpeg-test.mp4`、`test-kf-*.jpg` 为开发手测遗留文件，建议手动清理。

## 失败详情与建议

无代码缺陷导致的用例失败。唯一首轮失败 M2 分析如下：

- **M2 首轮（会话历史污染）**：连续追问后，多轮历史（最近 3 轮）中已含「大象鼻子长」等内容，模型合理选择不调用工具直接作答，toolsUsed 为空数组。这是 Agentic 设计的合理行为，但使 M2 用例对会话状态敏感。建议：后续测试 M2 类用例放在会话首问执行，或先 DELETE videoId 清空会话再测。
- 测试端伪影（非服务端缺陷）：H1 首轮 curl 中文经 Windows 控制台被 GBK 转码导致「乱码」，改用 UTF-8 的 Node fetch 复验无乱码。
