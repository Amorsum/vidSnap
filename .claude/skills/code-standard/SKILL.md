# code-standard — 代码规范化

目标：在**不改变功能行为**的前提下，让代码更规范、更简洁、更易维护。

## 执行步骤

1. **确定范围**：
   - 用户指定文件/目录 → 只处理指定范围；
   - 未指定 → 处理当前未提交改动（`git status --porcelain` + `git diff --stat`）涉及的文件；
   - 两者都没有 → 报告「无可规范的内容」，结束。
2. **逐项检查**（按此顺序，每处修改前先用 Grep/Read 确认所有引用点）：
   - **死代码**：未使用的 import / 变量 / 函数 / 导出、死参数、不可达分支、注释掉的代码块 → 删除
   - **重复代码**：同文件或跨文件的重复实现（类型定义、常量、逻辑块、样式片段）→ 提取为共享定义
   - **冗长代码**：过深嵌套 → 提前 return；重复条件表达式 → 提取布尔变量；可简化的写法（解构、可选链、三元替代 if/else 赋值等）
   - **注释规范**：删除复述代码的无意义注释；为「为什么这样做」的非显然逻辑补充注释；统一为中文注释，与仓库现有风格一致
   - **命名规范**：变量/函数名与实际用途一致，消除误导性命名、无意义缩写、拼音
   - **风格一致**：与相邻代码及仓库整体风格保持一致（引号、分号、尾逗号、缩进、导入顺序）
3. **硬性约束（必须遵守）**：
   - **只做等价重构**：不改变任何业务行为，禁止顺手"改进功能"或调整逻辑顺序
   - **不引入新依赖**，不修改 package.json
   - **不动关键协议/接口**：SSE 事件格式、API 请求/响应结构、转写降级链路等对外契约一律保持原样
   - **尊重项目特殊性**：本项目是 Next.js 16.2.10，与常见版本有 breaking changes —— 触及 Next.js API（路由、页面、组件）前先读 `node_modules/next/dist/docs/` 中相关指南，遵守 AGENTS.md 的要求
   - 拿不准是否安全的地方：**不改**，列入报告让用户决定
4. **验证**：
   - `npx tsc --noEmit` 必须通过；
   - 改动涉及页面/组件/路由时，`npm run build` 确认构建通过；
   - 有对应功能可测时（如解析流程）说明验证方式。
5. **汇报**：列出改动清单（文件 + 改了什么 + 为什么），并说明「行为未变」的依据（tsc/build 通过等）。

## 规则

- 质量优先于数量：不确定的改动不如不改。
- 一次只清理一类问题，避免大范围无差别重写。
- 清理结果不自动提交；用户确认后可交由 git-committer 提交。
